# Templates

Templates are reusable JSON fragments that can be mixed into a mod's capabilities via the `include` field in `manifest.json`. They are used to share region definitions, logic strings, and vocabulary data across multiple mods without duplication.

---

## Purpose

The primary use case for templates is **sharing region definitions** between related mods for the same game. For example, if your game has a set of progression regions with complex option-dependent access logic, those regions can be defined once in a template and included by any mod that needs to reference them — rather than re-declaring them in each manifest.

Templates are also used for:
- Vocabulary validation files (`Items.json`, `Locations.json`, `Regions.json`) — lists of valid names used to catch typos at manifest load time
- Base option templates (`default_options.json`) — starter YAML option stubs

---

## The `include` Field

In `manifest.json`, the `include` field inside `capabilities` accepts a list of paths to template JSON files:

```json
"capabilities": {
    "include": ["mymod/regions.json"],
    "items": [ ... ],
    "locations": [ ... ]
}
```

Paths are relative to `Templates/<GameName>/`. For a game named `Mygame`, `"mymod/regions.json"` resolves to `Templates/Mygame/logic/mymod/regions.json`.

The template file is merged into the mod's capabilities **before** the rest of the `capabilities` object is processed. Any regions, items, or locations declared in the template are prepended to the lists from the manifest.

### Template File Format

A template file contains a subset of the `capabilities` object — only the keys it contributes:

```json
{
    "regions": [
        { "name": "Mountain Pass" },
        { "name": "Deep Caves", "logic": "(Option: logic_difficulty == easy) OR (Item: Iron Key)" },
        { "name": "Crystal Sanctum", "logic": "(Item: Iron Key) AND (Item: Crystal Key)" }
    ]
}
```

A template can contain any combination of `regions`, `items`, and `locations` keys. Only those keys are merged. The template format mirrors the manifest `capabilities` structure exactly — each entry uses the same fields (`name`, `logic`, `amount`, `type`, etc.). Template item entries support the full `amount` expression grammar — `"fill"`, `{key}`, `{key}%`, and ternary forms are all valid inside a template, identical to their behavior in the declaring manifest.

## Directory Structure

```
Templates/
├── default_options.json           ← Base option stubs for YAML generation
└── <GameName>/                    ← e.g., Mygame/
    ├── Items.json                 ← Vocabulary: valid item names
    ├── Locations.json             ← Vocabulary: valid location names
    ├── Regions.json               ← Vocabulary: valid region names
    └── logic/                     ← Logic template fragments
        └── <modname>/
            └── regions.json       ← Region definitions for this mod
```

The `<GameName>` folder name must match the game name used by the framework (set in `framework_config.json` as `game_name`).

## Vocabulary Validation

When a mod's manifest has `"vocab_validation": true`, the framework validates all item, location, and region names against the game's vocabulary files:

- `Templates/<GameName>/Items.json` — list of valid item names
- `Templates/<GameName>/Locations.json` — list of valid location names
- `Templates/<GameName>/Regions.json` — list of valid region names

Any name not found in the corresponding vocabulary file produces a warning during manifest loading. This is useful for large mods where typos are hard to catch manually.

Vocabulary validation is opt-in per manifest. Mods that don't need it (e.g., small mods or mods that use fully dynamic names) can omit the field.

### Vocabulary File Format

Each vocabulary file is a JSON object with a single array key:

```json
{
    "items": ["Iron Key", "Crystal Key", "Lantern", "Data Shard", ...]
}
```

```json
{
    "locations": ["Mountain Pass: Supply Cache", "Caves: Hidden Alcove", ...]
}
```

```json
{
    "regions": ["Mountain Pass", "Deep Caves", "Crystal Sanctum", ...]
}
```

Vocabulary files are typically generated by game-specific import tools from game data exports rather than maintained by hand for large games.

## Adding Templates for a New Game

To add template support for a new game:

1. **Create the game folder:**
   ```
   Templates/<YourGame>/
   ```

2. **Add vocabulary files** (optional, only needed if using `vocab_validation`):
   - `Items.json` — all valid item names
   - `Locations.json` — all valid location names
   - `Regions.json` — all valid region names

3. **Add logic template files** for any regions you want to share across mods:
   ```
   Templates/<YourGame>/logic/<modname>/regions.json
   ```

4. **Reference in your manifest:**
   ```json
   "capabilities": {
       "include": ["modname/regions.json"],
       ...
   }
   ```

5. **Publish in a registry** so players can install directly via APF Manager — see [publishing.md](publishing.md) for how to structure the `Templates/<GameName>/` directory in a GitHub registry repo.

## Example: Shared Regions Template

`Templates/Mygame/logic/mymod/regions.json`:

```json
{
    "regions": [
        { "name": "Mountain Pass" },
        {
            "name": "Deep Caves",
            "logic": "(Option: logic_difficulty == easy) OR (Item: Iron Key)"
        },
        {
            "name": "Crystal Sanctum",
            "logic": "(Item: Iron Key) AND (Item: Crystal Key)"
        },
        {
            "name": "Boss Chamber",
            "logic": "(Item: Iron Key) AND (Item: Crystal Key) AND (Item: Lantern)"
        }
    ]
}
```

A companion mod's manifest includes this template to access the shared regions without duplicating the logic:

```json
"capabilities": {
    "include": ["mymod/regions.json"],
    "items": [ ... ],
    "locations": [
        { "name": "Boss Chamber: Secret Chest",
          "logic": "(Can Access: Boss Chamber) AND (Option: include_traps)" }
    ]
}
```

When the framework processes the companion mod's capabilities, the shared regions are merged in first, so `(Can Access: Boss Chamber)` in the location logic correctly references a known region.

---

## default_options.json

`Templates/default_options.json` is a base template for YAML generation — it documents the standard APF base options and their defaults. It is used by the YAML generator tool as a starting point when creating player YAML files, not by the framework during manifest loading.
