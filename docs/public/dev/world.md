# The APF apworld

`apf.apworld` is the Archipelago world file that handles generation for any game using AP Framework. It is game-agnostic: all game-specific content (items, locations, regions, goals, options) is declared in mod manifests and delivered to the apworld as a base64-encoded JSON blob embedded in the player's YAML file.

A single apworld installation supports any number of games simultaneously — each player selects their game by using the YAML generated by APF Manager, which includes the `capabilities_data` option pre-populated with that game's manifest data.

---

## How It Differs from Standard AP Worlds

Standard Archipelago worlds declare their items and locations as Python `ClassVar` dictionaries at module import time. `apf.apworld` cannot do this — the item/location set depends on which mods the player has installed and which options they selected.

Instead, `apf.apworld`:

1. Reads the `capabilities_data` option from the YAML (base64-encoded JSON built by the framework from all active mod manifests)
2. Decodes and processes this data in `generate_early()` — the first method called per-player during generation
3. Dynamically populates `item_name_to_id` and `location_name_to_id` class-level dictionaries
4. Calls `_update_data_package()` to force-refresh Archipelago's pre-built data package snapshot with the actual mappings

The `_update_data_package()` call is essential. Archipelago snapshots `network_data_package["games"][game]` at module import time when the ClassVars are still empty dicts. Without the refresh, the game appears to have no items or locations in the multiworld.

## Generation Flow

For each player slot using `apf.apworld`:

```
generate_early()
    └── decode base64(capabilities_data) → capabilities dict
    └── _process_capabilities()    — unwrap nested structure, validate required fields
    └── _filter_by_logic()         — remove always-false entries (option-gated pruning)
    └── _apply_item_overrides()    — apply cross-mod item type changes
    └── _build_region_table()      — dict of region_name → logic_string
    └── build_item_table()         — dict of item_name → ItemData(code, type, ...)
    └── build_location_table()     — dict of location_name → LocationData(code, region, ...)
    └── check_id_conflicts()       — detect + remap any ID collisions with other worlds
    └── _update_data_package()     — refresh Archipelago's pre-built data package

create_regions()
    └── Create Region objects for Menu + all declared regions
    └── Connect regions via entrance rules (from region logic)
    └── Attach Location objects to their AP regions

create_items()
    └── Create Item objects for all non-pruned items
    └── Fill remaining slots with filler/trap items (weighted by options)

set_rules()
    └── For each location: parse logic → compile CollectionState rule → set_rule()

set_completion_rules()
    └── Parse goal logic → compile → set_completion_condition()
```

## Logic Modes

The `logic_mode` option controls how sphere logic is enforced:

**`none` (0):** All locations are placed in a flat "Main" region accessible from the start. No access rules are set. Effectively sphere 0 for everything — useful for sanity checks or games with no meaningful progression gating.

**`basic` (1) — default:** Regions are created with access rules derived from their `logic` fields. Locations are placed in the AP region derived from their first `(Can Access: R)` node. Access rules are compiled from location logic strings using `LogicParser.compile_rule()`, producing Archipelago `CollectionState` lambdas.

In basic mode:
- A location with `"logic": "(Can Access: Zone Beta) AND (Item: Key)"` is placed in the `Zone Beta` AP region
- That region has an entrance rule from `Menu` based on its own access logic
- The location additionally has an item access rule for `Key`
- If the location has no `(Can Access:)` node, it is placed in `Main` (sphere 0)

## Base Options

These options are always available in every `apf.apworld` YAML, regardless of which game mods are active:

| Option key | Type | Default | Description |
|---|---|---|---|
| `capabilities_data` | text | (required) | Base64-encoded capabilities JSON. Generated automatically by APF Manager. |
| `logic_mode` | choice: `none`, `basic` | `basic` | Whether region logic is enforced during generation. |
| `filler_item_weight` | range 1–10 | `5` | Weight multiplier for filler items when padding the item pool. |
| `trap_item_chance` | range 0–100 | `10` | Percentage chance for filler item slots to become trap items (requires trap items in the pool). |
| `apf_log` | choice: `trace`…`error` | `warn` | Minimum log level for apworld debug output during generation. Intended for development use only. |
| `apf_logfile` | text | (empty) | File path to write generation logs to. Leave empty for console output. |

Game-specific options (declared in mod manifests) are merged into the YAML alongside these base options during YAML generation.

## Capabilities Data Format

The `capabilities_data` value is a base64-encoded JSON object produced by the framework during the GENERATION lifecycle phase. Its structure:

```json
{
    "version": "1",
    "game": "YourGame",
    "checksum": "a1b2c3d4",
    "capabilities": {
        "regions": [
            { "name": "Zone Alpha", "logic": "" },
            { "name": "Zone Beta",  "logic": "(Item: Key A)" }
        ],
        "items": [
            { "name": "Key A", "type": "progression", "amount": 1, "mod_id": "author.mygame.mymod" },
            { "name": "Coin",  "type": "filler",      "amount": 10, "logic": "" }
        ],
        "locations": [
            { "name": "Alpha: Chest", "logic": "" },
            { "name": "Beta: Vault",  "logic": "(Can Access: Zone Beta) AND (Item: Key A)" }
        ],
        "goals": [
            { "name": "all_keys", "display": "Collect All Keys", "logic": "(Item: Key A)" }
        ],
        "item_overrides": [ ... ]
    },
    "options": {
        "option_key": "value"
    }
}
```

The `checksum` field is used by the framework and apclientpp to validate that the game's data package matches the server's records. If the checksum mismatches, the framework enters ERROR_STATE with `CHECKSUM_MISMATCH`.

The `options` object carries option default values used by the apworld to evaluate option-gated logic during generation.

## Option Pruning

During `_filter_by_logic()`, the apworld evaluates each entry's `logic` field against the player's current option values. Entries that simplify to `Const(false)` — meaning they can never be satisfied with those options — are removed before any items or locations are created.

This is the mechanism behind option-gated content:

```json
{ "name": "Glitch Bomb", "type": "trap", "amount": 2, "logic": "(Option: enable_traps)" }
```

If `enable_traps` is `false`, this item's logic is `Const(false)` → it is pruned. The item pool never includes Glitch Bomb for that player. No special handling in the apworld is required — it happens automatically via `is_always_false(logic, option_values)`.

## ID Assignment

Item and location IDs are assigned from a base of `6942067`. The framework assigns each item and location a stable numeric ID based on its name and source mod. These IDs are embedded in the `capabilities_data`.

If a conflict is detected (two items or locations with the same ID), `check_id_conflicts()` auto-remaps the conflicting IDs and logs a warning. In practice, conflicts are rare because each mod's items and locations are namespaced.

---

## Multi-Mod Composition

When multiple mods are active simultaneously, the framework merges their capabilities before producing `capabilities_data`:

**Regions:** If two mods declare a region with the same name, their access logic is OR-merged: `(logic_A) OR (logic_B)`. This means a region becomes accessible if either mod's condition is met.

**Items and locations:** Each mod contributes its own items and locations independently. Names must be unique within a mod but can overlap across mods if intended (item overrides handle the case where Mod B wants to change Mod A's item type).

**Item overrides:** Processed in declaration order. If multiple mods override the same item, the last override wins.

**Location overrides:** OR-merged in declaration order. Each additional override adds another branch to the location's access logic.

**Goals:** All goals from all mods are aggregated. If more than one goal exists across all active mods, a `goal` text-choice option is auto-generated, and players select which goal to pursue in their YAML.

## Creating a Game-Specific apworld

`apf.apworld` is designed to work as-is for any game. To create a game-specific subclass (for custom game name, different defaults, or game-specific overrides):

1. Copy `worlds/apf/` to `worlds/yourgame/` in your Archipelago installation
2. In `__init__.py`, change:
   ```python
   game: ClassVar[str] = "YourGame"
   ```
3. Optionally override `create_items()`, `create_regions()`, or other methods for game-specific behavior

Most games do not need a subclass — the base `apf.apworld` handles everything through the capabilities data.
